# proto3 optional fields synthesize underscore-prefixed oneofs that must be skipped in ONEOF-element lint rules

## Problem

A new buf-parity ONEOF rule (`naming/snake-case-oneofs`) emitted false-positive findings on proto3 `optional` fields. The rule walked every `OneofDescriptor` exposed by the descriptor pool without distinguishing user-declared oneofs from compiler-synthesized wrappers, causing a routine proto3 idiom to surface lint findings the user could not action.

## Symptoms

- A proto3 file containing `optional string email_address = 1;` (and zero user-authored `oneof { ... }` blocks) produced a `naming/snake-case-oneofs` finding naming the synthetic oneof `_email_address`.
- The false positive scaled linearly with the number of `optional` fields in the file.
- The snake_case regex was functioning correctly — leading-underscore names are not in its character class — but the rule should not have been inspecting the synthetic oneof descriptor at all.

## What Didn't Work

The first cut of the rule walked oneofs naively (commit `6026151`):

```python
@lint_rule(
    rule_id="naming/snake-case-oneofs",
    severity=LintSeverity.ERROR,
    profiles=("recommended", "default"),
    element=ElementKind.ONEOF,
    message_template="Oneof {name!r} is not snake_case",
    source_spec="buf:ONEOF_LOWER_SNAKE_CASE",
)
def check_snake_case_oneofs(ctx: OneofLintContext) -> None:
    """Fire on oneof names that don't match snake_case."""
    if not _SNAKE_CASE_RE.match(ctx.oneof.name):
        ctx.emit(
            violation_kind="naming/snake-case-oneofs",
            params={"name": ctx.oneof.name},
        )
```

The regex correctly rejected `_email_address`, but the rule's *frame* was wrong: it was being invoked on a descriptor the user did not author, so any finding emitted from that invocation was noise. Tightening or loosening the regex would not have addressed the root cause.

## Solution

Add a leading-underscore skip guard as the first statement in the rule body (commit `9fae6e9`):

```python
def check_snake_case_oneofs(ctx: OneofLintContext) -> None:
    """Fire on oneof names that don't match snake_case.

    Skips proto3 synthetic oneofs generated by ``optional`` fields.
    The protobuf compiler synthesizes a wrapper oneof for each
    ``optional <type> <name>`` declaration and names it
    ``_<field-name>``. The leading underscore is a reliable
    discriminator because protobuf grammar prohibits user-authored
    oneof names from starting with an underscore: any oneof whose
    name begins with ``_`` is therefore compiler-synthesized rather
    than user-declared, and a snake_case finding on the synthetic
    name would be a false positive on a common proto3 idiom. This
    matches buf's ONEOF_LOWER_SNAKE_CASE which similarly excludes
    synthetic oneofs from its check.
    """
    if ctx.oneof.name.startswith("_"):
        return
    if not _SNAKE_CASE_RE.match(ctx.oneof.name):
        ctx.emit(
            violation_kind="naming/snake-case-oneofs",
            params={"name": ctx.oneof.name},
        )
```

The verifying test (`tests/schema/lint/rules/test_naming_extended.py::TestSnakeCaseOneofs::test_proto3_optional_synthetic_oneof_skipped`) compiles a fixture with two `optional` fields and asserts zero findings:

```python
_ONEOF_PROTO3_OPTIONAL = """
syntax = "proto3";
package optfield;

message User {
  optional string email_address = 1;
  optional int64 user_id = 2;
}
"""

def test_proto3_optional_synthetic_oneof_skipped(self, tmp_path):
    report = _run_single(
        tmp_path,
        {"optfield.proto": _ONEOF_PROTO3_OPTIONAL},
        "naming/snake-case-oneofs",
    )
    assert report.findings == ()
```

## Why This Works

Proto3 `optional` fields are not natively optional at the wire-format level — the compiler wraps each `optional <type> <name>` declaration in a synthetic `oneof` named `_<field-name>` to track field presence. This is implemented identically across protoc, protoxy, and the protobuf-python runtime: all of them surface the synthetic oneof as a `OneofDescriptor` on the parent message, and all of them use the leading-underscore convention.

The protobuf grammar explicitly prohibits user-authored oneof names from starting with an underscore — names must match `[a-zA-Z][a-zA-Z0-9_]*`. Therefore *any* `OneofDescriptor` whose name begins with `_` is guaranteed compiler-synthesized rather than user-declared. The leading-underscore test is a zero-cost, no-extra-import discriminator. The alternative — round-tripping through `CopyToProto` to inspect `FieldDescriptorProto.proto3_optional` on the contained field — works, but adds an unnecessary serialization step when the descriptor field's name already encodes the discriminator. The CopyToProto pattern IS the correct choice for proto-form-only fields that have no runtime-API alternative (e.g., `FileDescriptor.public_dependency` / `weak_dependency`); see [[copytoproto-round-trip-for-proto-form-only-descriptor-fields-2026-05-13]] for the affirmative-use side of the decision boundary.

This matches buf's own `ONEOF_LOWER_SNAKE_CASE` implementation, which similarly excludes synthetic oneofs. Without this skip, protokit's `recommended` profile diverged from buf parity on any proto3 file using `optional`.

## Prevention

- **Pattern for all future ONEOF-element lint rules**: open the rule body with `if ctx.oneof.name.startswith("_"): return`. The skip is cheap, safe, and well-defined; add it preemptively rather than waiting for the false positive to surface in a user PR.
- **Fixture discipline at unit-implementation time**: when shipping a buf-parity ONEOF rule, include a fixture using `optional` fields in the per-rule test class before the PR. Treat absence of the synthetic-oneof regression test as P2 review-blocking missing coverage.
- **Generalize the skip discipline to other compiler-synthesized descriptor objects**: this pattern recurs across descriptor kinds. For map fields, the discriminator is `GetOptions().map_entry` on the synthesized `<Field>Entry` nested message (see `check_pascal_case_messages` for the parallel guard, and the April 2026 compat-engine work [[matcher-backend-path-resolution-skew-silently-empties-output-2026-05-02]] which surfaced the same compiler-synthesis trap on field rules). When writing a rule at *any* element kind, ask the question: "does the protobuf compiler synthesize descriptor objects at this kind, and how would my rule observe them?" — and add the appropriate skip before walking.
- **Document the discriminator on the rule docstring**: future readers should understand the *grammar-derived* reason the skip is safe, not just see an unexplained `startswith("_")` check.
