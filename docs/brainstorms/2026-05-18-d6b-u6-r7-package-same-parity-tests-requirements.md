## TL;DR

U6 establishes the **protokit-vs-buf-recorded regression gate** for the R7 PACKAGE_SAME_* family AND ships the **multi-file harness extension** that D6c R8 (`package/same-directory`) will reuse. The parity contract is **partial-parity scoped to PACKAGE_SAME_* rule_ids** — protokit's R7-family findings byte-match buf v1.69.0's PACKAGE_SAME_* findings on identical multi-file inputs, per-fixture. Non-R7 rules (D6a families, future rules) are explicitly outside the assertion scope; the framing reflects the test's actual contract.

**Honest framing on value:** U6's value is narrower than "full byte-parity" wording would imply. U4a's 21 SHA-pinned `_buf_smoke/recorded/*.json` snapshots empirically captured buf v1.69.0's emit-shape (sort, bool rendering, inner-quote escape, mixed-presence template); U4b implemented the helper to match those observations. U6 closes the regression-detection gap between *helper-author intent* (asserted by ~80 internal tests in `tests/schema/lint/rules/test_package_same.py` + `tests/schema/lint/test_cli_package_same_e2e.py`) and *implementation behavior on identical inputs to buf* (currently untested end-to-end). If U6 lands with 21/21 passing on first run (the S4 expectation), the unit's value reduces to regression-insurance for future helper edits + a reusable harness for R8. If divergences surface, the unit catches them before U7's default-on flip. Either outcome is real; the latter is what the unit is built to make catchable.

**Three deliverables:**

## Problem Frame

After D6b U4b shipped, the 7 PACKAGE_SAME_* rules are operational as dormant code (importable, exercised via `--rule-pack` opt-in, NOT in `BUILTIN_PACKS`). Their unit and e2e tests are extensive: `tests/schema/lint/rules/test_package_same.py` (1200 lines) + `tests/schema/lint/test_cli_package_same_e2e.py` (326 lines) cover the R7 family with hand-written expected findings against protokit-internal fixtures. This proves the rules implement *what the helper author wrote down* — a real claim, not circular, because the helper was authored against U4a's empirically-captured buf observations. What it does NOT prove is implementation behavior on identical inputs to buf for the regression-detection use case.

The 21 SHA-pinned `_buf_smoke/recorded/*.json` snapshots committed at U4a are an empirical resource specifically designed to answer the parity question — but no test currently uses them to verify protokit's output against buf's. Today they only verify buf's output against itself (via SHA-pin) and against future buf releases (via live-mode `test_buf_smoke_assumptions.py`).

**The value U6 closes is regression-detection on a narrowly-defined contract.** U7 is the delivery-boundary unit that registers R7 in `BUILTIN_PACKS`, bumps to 0.3.0, and ships R7 as default-on. If a future helper edit introduces drift (e.g., a refactor changes the inner-quote-escape sequence, or a contributor "improves" the value-payload sort to first-encountered), the existing protokit-internal tests would either ALSO be updated (covering up the drift) or fail loudly without telling the maintainer whether protokit or the test was the wrong side. The U6 parity tests are the second line of defense: they assert protokit's PACKAGE_SAME_* output matches buf's recorded snapshots byte-for-byte on the same multi-file inputs, scoped per-fixture to the rule_id named in `buf.yaml use:[]`. A helper-edit-induced divergence shows up as a U6 failure naming the exact fixture + rule_id + protokit/buf finding diff, with the SHA-pin guaranteeing the recorded snapshot still represents buf v1.69.0 faithfully.

**The honest framing on value magnitude:** if U6 lands 21/21 passing on first run (the S4 expectation), the unit's value reduces to regression-insurance for future helper edits + a reusable harness for R8 in D6c. That value is real but smaller than "byte-parity verification" wording would imply. If divergences surface, U6 catches them before U7's default-on flip and pays for itself unambiguously. Either outcome justifies the unit; the framing throughout this brainstorm reflects the narrower-but-real contract rather than the broader-but-rhetorical one.

The parity-test infrastructure also needs a one-time extension. Today's `tests/parity/conftest.py` invokes both `protokit lint` and `buf lint` ONE proto file at a time (the single-file `run_protokit_lint`/`run_buf_lint` helpers + the single-file `assert_parity`). R7 is the project's first multi-file rule family — disagreement detection requires invoking the linter with ALL files in a package at once. R8 in D6c is the next known multi-file rule (1 known future consumer; N=1 reuse). The harness extension lands with N=1-justified weight; the abstraction earns full keep when R8 actually validates the shape.

**Alternatives considered:**

- *Skip U6, fold parity into U4b's existing unit tests.* Rejected — U4b's tests already shipped (1875-passing suite, ce:review + ce:compound complete). Retrofitting parity into them would require reopening U4b's scope after delivery boundary; clean separation honors the per-delivery workflow.
- *Skip U6, fold parity into U7 as the first commit (before BUILTIN_PACKS flip).* **Viable alternative; not adopted in this brainstorm.** Argument for folding: saves one full unit's ce:plan + ce:review + ce:compound ceremony cycle; commits remain separable within U7 (parity tests in commit 1, BUILTIN_PACKS flip in commit 2, version bump + CHANGELOG fold in commit 3); parity contract still verified before the flip. Argument against folding (and the brainstorm's choice): the unit-split surfaces parity drift in a focused ce:review pass dedicated to the parity contract specifically, rather than mixed with delivery-boundary concerns (CHANGELOG, README, version-bump semantics, presence-ratchet test, stale-text sweep). The product-level tradeoff is real — choosing U6-as-standalone-unit accepts the per-unit overhead in exchange for cleaner separation of empirical-gate work from delivery-boundary work. Documented honestly so the next sequencing decision (D6c R8 parity) can weigh the same tradeoff with this data point.
- *Build a parallel `tests/parity/fixtures/package_same/` tree.* Rejected (see KD-1) — duplicates the SHA-pinned `_buf_smoke/` fixtures without information gain.
- *Live-mode parity tests (re-invoke buf at test time).* Rejected — `test_buf_smoke_assumptions.py` already covers buf-drift detection. U6's parity tests answer "does protokit match buf?" not "did buf change?"; the recorded snapshots are exactly the right baseline to assert against.
- *In-process Click `CliRunner` instead of subprocess invocation.* Rejected for **consistency with the established single-file subprocess pattern** at `tests/parity/conftest.py:370-390`. Subprocess exercises the same import-graph + entry-point a real user hits; cold-import overhead is acceptable at 21 sequential cases. `/ce:plan` to measure against the worst-case fixture (`googleapis-import`) to confirm the 30s subprocess cap holds. Documented to prevent the alternative re-surfacing at `/ce:review`.

### Harness — Multi-file invocation infrastructure

- **R24. Three new conftest helpers** added to `tests/parity/conftest.py`, each next to its single-file sibling:

  - `run_protokit_lint_multi_file(fixture_dir: Path, *, rule_pack: str | None = None, proto_paths: tuple[Path, ...] | None = None) -> tuple[ProtokitFinding, ...]` — recursively enumerates `*.proto` files in `fixture_dir` via `sorted(fixture_dir.rglob("*.proto"))`. **Recursion is REQUIRED**: `googleapis-import/google/api/*.proto` and `wkt-conflict/google/protobuf/*.proto` live two directories deep and produce the buf findings the parity test must match; a non-recursive glob would silently lint only the fixture-root `a.proto` and the parity assertion would fail for those two fixtures (verified: both are 3-file fixtures with two protos at depth-2). `proto_paths` defaults to `(fixture_dir,)` so the helper invokes `protokit lint --json -I <fixture_dir> [--rule-pack=...] <files...>` — locally-shipped WKT stubs (`wkt-conflict/google/protobuf/*.proto`) and googleapis imports (`googleapis-import/google/api/*.proto`) resolve against the fixture root without protokit's built-in WKT bundle shadowing them. **Subprocess `cwd=fixture_dir`** — matching the single-file helper at `tests/parity/conftest.py:388` so protokit's emitted `location` path is fixture-root-relative, aligning with buf's recorded NDJSON `path` field after `_normalize_buf_path` normalization at `conftest.py:427-440`. The `assert_parity_multi_file` helper relies on this alignment for the `(path, line)` byte-match. Returns findings sorted by `(path, line, col, rule_id)` for deterministic assertion. **Shadow-path contract**: (a) NIL — a `fixture_dir` containing zero `.proto` files raises `pytest.fail` with a clear message; (b) ERROR — subprocess exit code outside `{0, 1}` surfaces as `pytest.fail` (matching the existing single-file pattern at `tests/parity/conftest.py:400-405`). Subprocess discipline (30s cap + triple-arm exception guard) matches the existing single-file helper. **Latency**: empirically measured 2026-05-18 against the 3-file `googleapis-import` worst-case = ~0.07s per invocation; 21 sequential cases project to <2s total, well under the 30s cap and any reasonable CI timeout.

  - `parse_buf_recorded_snapshot(snapshot_path: Path) -> tuple[BufFinding, ...]` — reads buf's `--error-format=json` NDJSON shape (one finding per line; fields: `path`, `start_line`, `start_column`, `end_line`, `end_column`, `type`, `message`). Returns findings sorted by `(path, start_line, start_column, type)`. Empty files yield an empty tuple. The typed `BufFinding` shape (named tuple or dataclass) is reusable by R8 in D6c.

  - `assert_parity_multi_file(protokit_findings: Sequence[ProtokitFinding], buf_findings: Sequence[BufFinding], *, protokit_rule_ids: AbstractSet[str], fixture_scenario: str) -> None` — verifies per-file finding-set parity for the multi-file emit shape (all-disagreers-fire across N files). `protokit_rule_ids` scopes the comparison to the SINGLE PACKAGE_SAME_* rule_id that fixture's `buf.yaml use:[]` enables (per-fixture rule scoping per KD-7); other R7 rules + non-R7 rules (D6a families fired by BUILTIN_PACKS + R7 rules outside the per-fixture scope) are excluded from the assertion. **Two-sided rule-id check before assertion**: (i) every protokit finding inside `protokit_rule_ids` must pair with a buf finding; (ii) every protokit finding OUTSIDE `protokit_rule_ids` BUT inside the R7 family must NOT exist (over-firing complement — catches the case where a future helper edit makes `java_package` rule fire on a `go_package`-only fixture). Asserts: (a) finding counts match per file for the scoped rule_id, (b) each protokit finding's `(path, line, message)` byte-matches a buf finding with the equivalent rule-id mapping, (c) no orphan findings on either side. Sort-key uniqueness within each side is asserted before pairing (catches the case where multiple findings share `(path, line, col, rule_id)` and positional pairing would break). Diagnostic message names the fixture_scenario for fast triage.

- **R25. Collection-time invariants** (4 guards in `test_parity_package_same.py`):

  - `test_every_package_same_rule_has_at_least_one_firing_fixture` — walks the R7 family in `protokit.schema.lint.rules.package_same.RULES`, builds the expected-fires map from the recorded snapshots, asserts every R7 `rule_id` appears in at least one snapshot's firing set. Catches "added an R7 rule but forgot to back it with a fixture." (Honest framing: this is a fixture-coverage smoke check, not a correctness signal — over-firing is caught by the `assert_parity_multi_file` two-sided rule-id check at test time per R24, not by this invariant.)

  - `test_fixture_list_matches_smoke_assumptions` — asserts U6's locally-iterated fixture set equals `tests.schema.lint.test_buf_smoke_assumptions._SMOKE_FIXTURES`. Catches "added a smoke fixture but forgot the parity test" and "U6 silently re-defined the fixture list."

  - `test_every_recorded_snapshot_is_reachable` — **bidirectional invariant**: (a) every `recorded/*.json` file (explicit `.json` suffix filter, excludes `CHECKSUMS.sha256`) corresponds to a `_SMOKE_FIXTURES` entry; (b) every `_SMOKE_FIXTURES` entry has both a fixture directory at `_buf_smoke/<scenario>/` AND a recorded snapshot at `_buf_smoke/recorded/<scenario>.json`. Catches orphan snapshots (e.g., U4a added a snapshot, U6 was written before that snapshot landed), missing snapshots (entry added to `_SMOKE_FIXTURES` but recorded file never committed), and fixture/snapshot rename drift in one pass. A forward-only check (only (a) without (b)) would miss the missing-snapshot direction; the bidirectional version is the value-add over either single-direction check.

  - `test_every_fixture_buf_yaml_pins_one_r7_rule` — parses each fixture's `buf.yaml` via `yaml.safe_load` (PyYAML is already in dependencies at `pyproject.toml`, `PyYAML>=6.0,<7` + `types-PyYAML`; security note: NEVER `yaml.load()` without explicit SafeLoader). **Parsing contract**: (i) read the TOP-level `lint.use` key only — module-scoped `lint.use` (legal in buf v2 schema under `modules[].lint.use`) is NOT consulted; if a fixture's top-level `lint.use` is missing/empty, the invariant fails at collection time naming the fixture with a hint to consolidate at the top level. (ii) accept both block-style (`use:\n - PACKAGE_SAME_X`) and flow-style (`use: [PACKAGE_SAME_X]`) — `yaml.safe_load` handles both. (iii) missing `buf.yaml` file raises `FileNotFoundError` re-raised with the fixture name in the message. (iv) malformed YAML re-raises with the fixture name. Asserts `lint.use` is a single-element list whose value maps to a known protokit R7 `rule_id` via `_extract_buf_rule_id(spec.source_spec)`. Catches "fixture lists multiple PACKAGE_SAME_* rules" (would break per-fixture scoping) and "fixture lists a buf rule_id with no protokit counterpart" (would break R25(a)'s rule-id mapping). This is the load-bearing precondition for KD-7's per-fixture rule-scoping approach.

  - `test_buf_yaml_rule_matches_recorded_findings_rule` (R25(e), per ADV-7) — for each NON-EMPTY recorded snapshot (`all-agree.json` and `wkt-only.json` exempt — empty by design), asserts the unique `type` field value across all findings equals the rule_id derived from that fixture's `buf.yaml use[0]` (via the buf-id-to-protokit-id mapping from `_extract_buf_rule_id`). Catches the drift mode where a contributor edits a fixture's `buf.yaml` without re-capturing the snapshot (or vice versa); without this check, per-fixture rule scoping could pass false-positive parity by comparing protokit's findings for the wrong rule_id against a snapshot's findings for a different rule_id.

## Scope Boundaries

- **BUILTIN_PACKS registration is U7's job.** U6 keeps R7 dormant and exercises it via `--rule-pack=...` opt-in. Flipping the default-on switch + 0.2.0 → 0.3.0 version bump + CHANGELOG-DRAFT fold + README refresh is the delivery-boundary work U7 owns.

- **No live-mode buf re-invocation in U6.** `test_buf_smoke_assumptions.py` (U4b, BUF_BINARY-gated) already validates buf v1.69.0's output against the recorded snapshots. U6's parity tests answer "does protokit match buf?" — re-invoking buf at U6 test time adds no information.

- **No new `tests/parity/fixtures/package_same/` tree.** The 21 `_buf_smoke/` fixtures + SHA-pinned recorded snapshots are the empirical source-of-truth; mirroring them under `tests/parity/fixtures/` would duplicate maintenance burden without information gain (see KD-1).

- **No adversarial fixtures added in U6.** Per A4's residual concern, fixtures stressing the helper outside its tested domain (values approaching the 500-char `_safe_for_stderr` cap, non-ASCII option values, comment-shifted line numbers, UTF-8 BOM, proto2 syntax) would widen the parity-confidence base. Adding them requires BUF_BINARY at fixture-creation time (to capture buf's actual output as the new ground truth) — a U4-style empirical-capture deliverable, not a U6-style parity-gate deliverable. ## Key Decisions

### KD-1. Hybrid fixture-source strategy (Approach C)

**Decision:** New parity test module under `tests/parity/test_parity_package_same.py` consuming the existing `_buf_smoke/` fixtures + recorded snapshots in place. No fixture duplication.

**Why not Approach A (reuse: parity tests collocated with `_buf_smoke/`)?** Breaks the established `tests/parity/` convention from D6a U8. Future contributors looking for "where do R7 parity tests live?" would not find them in the obvious location.

**Why not Approach B (mirror: build new `tests/parity/fixtures/package_same/` tree)?** Duplicates the SHA-pinned recorded snapshots without information gain. The 21 `_buf_smoke/` fixtures are committed precisely as the empirical source-of-truth; re-deriving them in a parallel tree adds maintenance burden, creates two locations for "the same fixture," and forfeits the dual-mode invariant (`test_buf_smoke_assumptions.py` already validates buf-actual against `_buf_smoke/recorded/`).

**Why Approach C?** Parity tests live where contributors expect (`tests/parity/`); fixtures stay where they are (single source of truth, SHA-pinned, snapshot-bound). Multi-file harness extension lives in `tests/parity/conftest.py` where D6c R8 will reuse it. The slight indirection (test module in one tree, fixtures in another) is offset by the three collection-time invariants that prevent silent drift.

### KD-2. Recorded-snapshot mode in the required `test` job (no BUF_BINARY, no parity-marker gate)

**Decision:** R20's parity tests assert protokit's output against the committed `recorded/*.json` snapshots, not against live buf re-invocation. The test module does NOT apply `pytestmark = pytest.mark.parity` — tests run in the default `pytest tests/` invocation that the required `test` CI job executes on every PR.

**Why drop the marker?** Per A1: the existing `parity` CI job (D6a U8) is documented INTENTIONALLY ADVISORY (`.github/workflows/ci.yml` per the conftest docstring: "DO NOT add to required-checks"). Applying `pytest.mark.parity` to U6's tests would gate them behind that advisory job, which silently undermines the value proposition ("per-PR coverage of the parity contract"). Since U6's tests have no BUF_BINARY dependency (recorded-snapshot mode is the whole point), they CAN run in the required `test` job — and should. The convention break is deliberate and bounded: U6 is the first `tests/parity/` module without the marker, justified by (a) no BUF_BINARY dependency, (b) the parity job's advisory status, (c) the value proposition requiring per-PR coverage.

**Why recorded-snapshot mode over live re-invocation?** The regression-detection edge U6 closes is `protokit → buf-recorded`. Live re-invocation re-tests `buf → recorded` (already covered by `test_buf_smoke_assumptions.py`). The SHA-pin in `test_buf_smoke_recorded_checksums.py` guarantees the recorded snapshots match what U4a empirically captured; that is the right baseline to assert protokit against.

**Future-proofing:** If buf v1.69.0 → newer-buf migration lands and the live-mode test surfaces drift, the recorded snapshots get re-captured (U4-style empirical pass) and U6's tests continue asserting against the new baseline. The decoupling is intentional.

### KD-3. Single-source-of-truth fixture list via cross-module import

**Decision:** R20's parametrize source imports `_SMOKE_FIXTURES` from `tests.schema.lint.test_buf_smoke_assumptions`. R25(b) collection-time invariant pins the relationship.

**Why?** Drift between U4b's live-mode buf-drift gate and U6's parity tests would silently leave a scenario uncovered by one or the other. A single tuple definition with an invariant test is cheaper to maintain than two parallel lists; the cross-module import explicitly documents the dependency.

### KD-4. `--rule-pack` opt-in (NOT BUILTIN_PACKS registration) for the dormancy window; flag becomes a deliberate no-op post-U7

**Decision:** R22's parity invocation passes `--rule-pack=protokit.schema.lint.rules.package_same`. R7 stays out of BUILTIN_PACKS until U7. **Post-U7, the flag is RETAINED as a deliberate no-op** — the LintEngine short-circuits duplicate pack loads by module name (`src/protokit/schema/lint/engine.py:241-242`: `if module.__name__ in self._loaded_module_names: return  # idempotent`). No U7 migration work required; no flag removal needed; no docstring TODO required.

**Why?** Honors the dormancy contract from U4b. Flipping the default-on switch is the documented delivery-boundary work U7 owns (paired with the 0.2.0 → 0.3.0 bump). U6's parity tests should exercise R7 in the same opt-in shape that real users would today (per the `--help` epilog line + CHANGELOG-DRAFT staging entry). Once U7 flips BUILTIN_PACKS, the `--rule-pack` flag still works correctly — the engine's idempotent load semantics mean the second load is silently dropped. Verified at HEAD (`5a3f86f`) via direct inspection of the engine's `load_rule_pack` implementation.

**Why retain rather than remove?** Retention preserves the test module's documentation value (the flag explicitly names the rule pack the test scopes itself to, even after BUILTIN_PACKS makes loading implicit) and avoids touching U6's test module at U7 — cleaner separation of empirical-gate work from delivery-boundary work, consistent with KD-2's philosophy. The test module's docstring should explain the no-op-post-U7 contract once at module-level rather than carrying a TODO comment.

### KD-5. New `assert_parity_multi_file` instead of overloading `assert_parity`

**Decision:** Add a sibling helper for multi-file emit shape rather than extending the existing single-file `assert_parity` signature.

**Why?** The single-file `assert_parity` takes `proto_relpath` + `expected_fires: bool` — semantics that don't generalize to multi-file all-disagreers-fire emission. Trying to overload `assert_parity` to handle both shapes would muddy the existing contract that 4+ parity test modules rely on. A sibling helper named for its shape (`_multi_file`) is the clearer extension.

### KD-6. Typed `BufFinding` shape in `parse_buf_recorded_snapshot`

**Decision:** The buf NDJSON parser returns typed records (named tuple or dataclass) rather than raw dicts.

**Why?** R8 in D6c will reuse the same shape; documenting the field set in code is cheaper than discovering it via grep later. Buf's `--error-format=json` field names (`path`, `start_line`, `start_column`, `end_line`, `end_column`, `type`, `message`) become the authoritative type contract for the parity tree.

### KD-7. Per-fixture rule scoping driven by `buf.yaml use:[]`

**Decision:** `assert_parity_multi_file(..., protokit_rule_ids={derived_rule_id})` scopes the parity comparison to the SINGLE PACKAGE_SAME_* rule_id named in each fixture's `buf.yaml use:[]` clause — NOT the full R7 family. R20 derives the per-fixture rule_id at collection time by parsing `<scenario>/buf.yaml`; R25(d) invariant pins the precondition that each fixture's `use:[]` has exactly one entry mapping to a known protokit R7 rule_id.

**Why?** Per A2 + F3: each `_buf_smoke/<scenario>/buf.yaml` enables exactly ONE PACKAGE_SAME_* rule (e.g., `use: [PACKAGE_SAME_JAVA_PACKAGE]`), so buf's recorded output only contains findings for that one rule. Protokit invoked with `--rule-pack=...package_same` loads ALL 7 R7 rules. Today's symmetry — that other R7 rules don't fire on a fixture targeting one specific rule — is **latent** because each fixture only sets the one option attribute. A future helper edit, a new smoke fixture that sets multiple options, or a refactor that accidentally fires `java_package` rule on `go_package`-only input would silently break parity unless the comparison is scoped per-fixture. Per-fixture scoping makes the contract rule-tight rather than family-tight; the over-firing complement in `assert_parity_multi_file` (R24) catches the case where protokit fires a non-scoped R7 rule on a fixture that shouldn't see one.

**Why not family-scoped (the original lean)?** Family-scoping (`protokit_rule_ids = frozenset(spec.rule_id for spec in RULES)`) would let an over-firing R7 rule silently pass parity by being filtered out alongside the legitimate non-R7 findings (D6a families). The latent-symmetry argument above is the falsification scenario.

**Why not assume the symmetry holds without scoping?** Trust-but-verify, per the project's verify-before-claiming discipline. The latent-symmetry assumption could break for any future smoke fixture; pinning it via per-fixture scoping + R25(d) collection-time invariant is cheaper than discovering the silent failure mode later.
