**Three deliverables grouped into 4-5 units:**

1. **R8 + R8b cross-file rule pair** — two architecturally-dual rules sharing one Arch-D pre-walk accumulator:
   - **R8 `package/same-directory`** — fires when files declaring the SAME package value are split across MULTIPLE directories. Buf parity rule_id `PACKAGE_SAME_DIRECTORY`. Per OQ-1 verification: per-file findings (one per disagreer file) with message text listing all directories holding the package (e.g., `"Multiple directories \"dir1,dir2\" contain files with package \"acme.foo\""`).
   - **R8b `package/directory-same-package`** — fires when files in the SAME directory declare DIFFERENT package values. Buf parity rule_id `DIRECTORY_SAME_PACKAGE`. Per OQ-1 verification: per-file findings (one per file in the affected directory) with message text listing all conflicting packages (e.g., `"Multiple packages \"acme.bar,acme.foo\" detected within directory \"dir1\""`).

## Problem Frame

The 17-of-18 buf BASIC parity gap shipped in 0.3.0 (D6b U7) is honestly documented in CHANGELOG.md `### D6b` and README's Schema Linting section: "the 18th, `package/same-directory`, defers to D6c due to its cross-file rule-kind architectural requirements." This pre-commits D6c to closing the gap.

The deferral was load-bearing for D6b's scope discipline. The D6b parent brainstorm framed R8's exclusion as "Tier 2 cut after 3-persona convergence" — scope-guardian + adversarial + product-lens flagged that the cross-file rule kind requires a new `ElementKind` value, a new `LintLocation` discriminant, an engine walker phase, and "an audit of every `match/case` over `LintLocation` in formatters per the cross-format-enum-string-parity discipline." That's a multi-module wire-format change worth its own focused delivery, not a Tier-2 add-on to D6b.

**Two brainstorm-level pressure-test findings revise the D6b framing:**

1. **The "audit every match/case over LintLocation" framing is over-stated** (verified at brainstorm time via `grep -rn "case .*Location\|match.*LintLocation" src/protokit/`). The current formatters do NOT use exhaustive match/case statements over `LintLocation` variants. Instead, they duck-type:
   - `_builtin_lint.py:161, 308, 399, 510` — `str(finding.location)` works via `__str__` (any new variant with `__str__` works automatically).
   - `_builtin_lint.py:311-313` — `type(finding.location).__name__.removesuffix("Location").lower()` works via reflection (any new `*Location` class works automatically).
   - `_builtin_lint.py:309` — `finding.location.file` is the ONLY production-formatter fragile site. Test-helper sites at `tests/parity/test_assert_parity_branches.py:35`, `tests/schema/lint/test_engine.py:226`, `tests/schema/lint/test_walk_coverage.py:209`, `tests/schema/lint/test_model.py:514`, `tests/schema/lint/test_cli_package_same_e2e.py:241`, `tests/schema/lint/rules/test_package_same.py:141, 594` also access `.file` (some via `# type: ignore[attr-defined]` slips) and need an audit pass. Every existing variant has a `.file` field; a new variant lacking `.file` would surface as `AttributeError` in `lint_json` formatter + several test failures.
   - **Documented exhaustiveness contract caveat:** the `LintLocation` docstring at `src/protokit/schema/lint/model.py:281-293` explicitly declares that consumers MUST end every `match` statement with `case _: typing.assert_never(loc)` — the design intent is exhaustive matching. The absence of such matches in-tree means in-tree code already lives outside the documented contract; third-party formatter packs that DO follow the contract would need a new arm if Scenario B (new variant) lands. Decision deferred to `/ce:plan`: (a) update the contract docstring to reflect duck-typed practice, (b) acknowledge third-party-pack impact in CHANGELOG migration recipe, or (c) audit + add `assert_never` to in-tree consumers proactively.
   The "audit every match/case" task reduces to "audit one duck-typed attribute access + ~7 test-helper sites + decide whether the new location has `.file` + decide what to do with the docstring exhaustiveness contract."

2. **The "needs new `ElementKind` + `LintLocation` discriminant" assumption is premature.** It depends on whether buf v1.69.0's `PACKAGE_SAME_DIRECTORY` produces per-file findings (existing `FileLocation` suffices; we need only a cross-file dispatch model) or per-directory findings (then we need new model types). This is an empirical verification, not an a-priori design choice. `/ce:plan` must run buf v1.69.0 against a curated package-mismatch fixture and inspect the JSON output's `location` shape BEFORE picking the architecture.

These findings narrow R8's architectural scope from "multi-module wire-format change" to "cross-file dispatch phase + at-most-one new model type." The "audit every formatter" framing was a worst-case worth pre-committing against, but the actual surface area is meaningfully smaller. D6c's headline framing should be **"cross-file lint rules now supported; first specimen: `package/same-directory`"** rather than **"wire-format-discriminant overhaul + R8."**

## Strategic Framing

D6c sits between two strategic threads:

- **Architectural-completion thread** (D6c): close 18/18 buf BASIC by adding the engine's first cross-file dispatch capability. Compounds for future cross-file rules (multi-file uniqueness, proto-versioning checks, package-scoped consistency rules).
- **Differentiator-expansion thread** (D6d+): grow the option-aware pack beyond R6's deprecated-replacement family. The "protokit reads custom options" claim matures with each new option-aware rule.

Pre-D6c scope decision (this brainstorm): **D6c is architectural-only.** The differentiator-expansion thread defers to D6d. Rationale: hybrid releases dilute both narratives; the 18/18 buf BASIC headline benefits from a clean CHANGELOG section; R8's cross-file dispatch design needs full design-attention to avoid premature abstraction.

**Compounding-value framing for the cross-file dispatch infrastructure:** R8 is the validation specimen for a capability D6c+ will reuse. Each future cross-file rule (proto-versioning between schema generations, FQN uniqueness across a FileSet, package-import-cycle detection) reuses this dispatch phase. R8 is the headline; the infrastructure is the durable value. CHANGELOG framing should lead with the infrastructure: "0.4.0 adds cross-file lint dispatch; the first cross-file rule is `package/same-directory`."

## Migration & User-Visible Impact

**Who sees new findings on 0.3.x → 0.4.0?**

Teams with multi-file `.proto` directories where the files declare different `package` values. Specifically:

- **No impact**: single-file directories; directories where all files share the same `package`; teams using `option java_package = "..."` / `option go_package = "..."` for language-specific overrides (those are governed by R7 PACKAGE_SAME_*, not R8).
- **Impact**: directories with mixed `package` declarations — uncommon in well-organized monorepos, occasionally found in migration states (a team refactoring `acme.user.v1` → `acme.user.v2` may have both packages temporarily coexist in `proto/acme/user/`).

**Migration recipe** (CHANGELOG section per [[builtin-packs-expansion-changelog-migration-recipe-structure-2026-05-18]]):

1. **Audit first** — `protokit lint <root> --severity=error 2>&1 | grep package/same-directory` to enumerate affected directories.
2. **Resolve at source** — pick the canonical package per directory; rename mismatched files' `package` declarations to match. Best long-term option.
3. **Per-rule demote** — `[tool.protokit.lint.severities] "package/same-directory" = "warning"` (sees signal without breaking CI) or `"off"` (silences entirely; tracking-debt).
4. **Pin to 0.3.x** — `pip install "protokit<0.4"`. Deferral fallback; not recommended long-term (no 0.4.x patches reach 0.3.x).

Plus "no pyproject.toml?" sub-section + 3 accepted-tradeoff scenarios (paths 3 + 4 don't address the underlying mixed-package state; teams accepting them should document why per [[buf-parity-divergence-documentation-discipline]]).
