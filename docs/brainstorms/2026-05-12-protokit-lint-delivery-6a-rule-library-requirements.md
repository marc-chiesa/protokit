# protokit-lint Delivery 6a — BASIC parity rule library + option-aware differentiator seed

## Problem Frame

After D5 (pyproject config + `--exclude`) shipped on 2026-05-12, `protokit lint` has a polished ergonomic substrate — pyproject discovery, four formatters, cross-formatter render parity, perf smoke, and full Public Surface DRAFT for 1.0 — but only **one rule** fires: the canonical `naming/snake-case-fields` canary that's been in place since D2.

The lint thesis is "we have an engine but no rules; the engine isn't useful without rules to fire." D6 is where that thesis becomes a product. Two strategic frames decided here:

**Adoption frame (forward bet, not current pain).** No team today runs both `buf lint` and protokit-lint for overlapping jobs — protokit's compat module is breaking-change checking, not lint. The "multi-tool fatigue" framing is a forward hypothesis: we believe that as protokit-lint grows, proto-using Python teams currently using `buf lint` plus protokit-compat will reach for protokit-lint as a Python-native replacement. BASIC parity is the precondition for that to be possible; once teams are running both lints, "uninstall buf" becomes a real choice. D6a invests in that future by shipping profile aliases (buf's category names resolve to protokit-native names) and parity-test infrastructure so we can prove and maintain equivalence. The bet may not pay off; if it doesn't, the same rules + parity tests still serve a smaller audience well.

**Differentiation frame.** Buf and other proto linters operate on descriptor metadata and can't easily introspect Protobuf custom options or attached source comments — protokit is Python-native and built on the descriptor pool with full access. Custom-option-aware rules are protokit's moat: nothing in the industry can directly replicate them. D6a ships one seed example to validate the path end-to-end; D6b grows the pack.

D6a is large enough that it warrants a multi-delivery split:

- **D6a (this brainstorm)** — buf BASIC parity in default profile for **single-language proto teams** + 1 option-aware differentiator seed + buf-mirrored profile aliases on protokit-native names + 3 of the D5-deferred config knobs that only become meaningful at 20-rule scale.
- **D6b (follow-on, not in this brainstorm's scope)** — expand to full buf DEFAULT parity, ship the cross-language `PACKAGE_SAME_*` family (multi-language teams' migration gate), per-rule disable/enable, grow the option-aware pack, and harden any D6a infrastructure gaps surfaced by real users.

The split is shippable-on-its-own: D6a is the meaningful adoption checkpoint for **single-language teams** running buf BASIC. Multi-language teams using buf's cross-language rules wait for D6b — this is an honest scope boundary, not a missed checkpoint.

## Requirements

### Auto-load surface expansion (KD-9 reconcile)

- R0. **Harmonize KD-9 with D5's pre-1.0 stability disclaimer and ship the auto-load expansion as a pre-1.0 minor-version bump with BREAKING marker.** `src/protokit/schema/lint/rules/__init__.py` KD-9 currently requires "the protokit major version is being bumped" for any `BUILTIN_PACKS` auto-load expansion. That clause pre-dates D5's pre-1.0 stability disclaimer (which explicitly permits breaking changes in pre-1.0 minor releases when flagged with `BREAKING:` in CHANGELOG). D6a amends the KD-9 docstring to: *"BUILTIN_PACKS auto-load expansion requires explicit intent: at pre-1.0, a minor-version bump (0.X → 0.X+1) with BREAKING CHANGELOG marker; post-1.0, a major-version bump."* Protokit version bumps from 0.1.0 to its next pre-1.0 minor (exact number picked in /ce:plan; 0.2.0 if treated as the first delivery-level BREAKING). CHANGELOG `BREAKING` marker enumerates: (a) BUILTIN_PACKS gains 5-6 new pack modules; (b) every existing protokit lint user sees N+1 categories of findings on previously-green CI runs; (c) opt-out path is `--no-builtin-rules` (per R9c) or pinning to the prior minor version. `tests/schema/lint/test_builtin_packs.py` is updated to match the new tuple in the same commit.

### Rule library — buf BASIC parity (default profile)

- R1. Ship the core buf-BASIC rule families. Primary profile membership is `recommended` (per R7's hierarchy: rules declare `profiles=("recommended", "default")` so they fire under both); `default` is `recommended` + the R6 differentiator. Families: naming, enum semantics, imports, package conventions, RPC conventions, and file conventions (file conventions cover both file-syntax-specified rules and file-naming rules; package conventions cover both package-defined / directory-match and package-lower-snake-case rules — `essentials` and `recommended` slice these families differently per R7). The 7 cross-language namespace-consistency rules (`PACKAGE_SAME_*` family — `go_package` / `java_package` / `csharp_namespace` / `php_namespace` / `ruby_package` / `swift_prefix` / `java_multiple_files`) are NOT shipped in D6a; they are deferred to D6b. D6a is honestly a single-language-team migration target.
- R2. Each shipped rule has a documented buf-rule-id equivalent in its `LintRuleSpec` docstring (e.g., `naming/enum-pascal-case` maps to `buf:ENUM_PASCAL_CASE`). The equivalence claim is testable per R10.
- R3. Approximate rule count for the default profile after D6a: ~20 rules across the six families (plus the 1 differentiator from R6). Exact rule inventory finalized during /ce:plan against buf's published BASIC category as of the planning date; ratchet up if buf has added rules.
- R4. The existing `naming/snake-case-fields` canary (D2) continues to fire under its current rule_id. No BREAKING rename.

### Option-aware differentiator seed

- R6. Ship `options/deprecated-must-have-replacement-comment`: when `FieldOptions.deprecated = true`, `EnumValueOptions.deprecated = true`, `MethodOptions.deprecated = true`, `MessageOptions.deprecated = true`, or `EnumOptions.deprecated = true` is set on the corresponding descriptor element, require a leading source comment that names the replacement (regex / keyword-based heuristic — `/use .* instead/i` family, finalized during /ce:plan). Proves the option-aware + comment-introspection path end-to-end without requiring new pyproject config schema. No buf analogue exists; this rule is protokit-only.
- R6a. **Enable `SourceCodeInfo` preservation in both compile backends as a D6a prerequisite for R6.** `src/protokit/_cli_utils.py:235` currently passes `include_source_info=False` to `protoxy.compile`, and `_compile_with_protoc` does not pass `--include_source_info` to `protoc`. R6's comment-introspection path requires `FileDescriptorProto.source_code_info.location[]` to be populated; without this prerequisite, R6 cannot read leading comments. Work includes: flip protoxy to `include_source_info=True`, add `--include_source_info` to the protoc command, refresh the "neither carries source-location info into the pool" comment, and document the descriptor-size impact (~10-30% larger serialized descriptor sets — measure during /ce:plan and document the actual delta in CHANGELOG). All D1-D5 functionality must continue to work unchanged; the existing cold-import contract and ratchet must hold.
- R6b. **Extend `CompileResult` to carry a source-location index built before `pool.Add()` discards `source_code_info`.** Second-pass feasibility review confirmed `DescriptorPool.Add(FileDescriptorProto)` discards `source_code_info` — `FileDescriptor.CopyToProto()` returns zero `location[]` entries after a pool round-trip, even when the input proto carried 16+ entries. R6a alone is insufficient; the lint engine receives `CompileResult.pool` (a `DescriptorPool`) with no path to read leading comments. R6b adds a new `CompileResult.source_locations: Mapping[str, FileDescriptorProto] | None` field populated FROM the `FileDescriptorSet` BEFORE pool.Add() consumes it (in `_compile_with_protoxy` at `_cli_utils.py:229-236` and `_compile_with_protoc` at `_cli_utils.py:283`). The lint context (`FieldLintContext` etc.) gains a `leading_comment(path: tuple[int, ...]) -> str | None` helper that walks the indexed `source_code_info.location[]` for the current descriptor's path. R6 (and all future comment-aware rules) uses this helper. The new field defaults to `None` for callers that don't request source info (preserving backward compatibility for D1-D5 paths). This work is in D6a scope as a structural prerequisite for R6 — without R6b, R6 cannot be implemented at all.

### Profile vocabulary

- R7. **Primary protokit profile names are protokit-native; buf-equivalent names are documented aliases.** Primary names: `essentials`, `recommended`, `default`. Buf aliases (resolved to primaries at config-load time): `minimal` → `essentials`, `basic` → `recommended`. (`default` is a universal lint-tool term; no buf-naming dependency. Each rule declares membership on the primary name only; the alias table lives in `_config.py` and resolves before `LintProfile.compose`.) Buf migrants get a 1-line config rewrite; protokit's identity is not permanently coupled to buf's category vocabulary. **Family-to-profile mapping mirrors buf's published category contents for the pinned buf version (R10 pin); exact rule inventory and per-profile counts finalize during /ce:plan against that pin.**
  - `essentials` (buf alias `minimal`) — file + package structure basics (buf MINIMAL equivalents: directory-same-package, package-defined, package-directory-match, package-same-directory, file-syntax-specified family).
  - `recommended` (buf alias `basic`) = `essentials` ∪ naming + enum + imports + RPC + file-naming families (full buf BASIC parity). This is the migration target for buf users moving to protokit (see Success Criterion 2 below).
  - `default` = `recommended` + the R6 differentiator. The existing `naming/snake-case-fields` canary (R4) is in `recommended` (and therefore in `default`) — D6a amends its membership from `profiles=("default",)` to `profiles=("recommended", "default")` so the hierarchy holds.
  
  `strict` is **not** in D6a — defer to D6b once strict-only rules are defined (e.g., COMMENT_* family, `ENUM_ZERO_VALUE_SUFFIX`, etc.). Shipping `strict` as a placeholder with a misleading rule count would damage the public surface; better to land it once it's substantive. Buf alias `strict` also waits for D6b. The hierarchy `essentials ⊂ recommended ⊂ default` is implemented via multi-profile declarations on each rule (`@lint_rule(..., profiles=("recommended", "default"))`), NOT via runtime profile inheritance — `LintProfile.compose()` unions rule_ids and does not implement subset expansion.
### Config knobs (D5 deferred to D6)

- R9. Ship three config knobs that only become meaningful at 20-rule scale, all pre-committed by D5 plan or D5 brainstorm. **Each pyproject key in R9a/R9c requires explicit expansion of `_ALLOWED_KEYS` in `src/protokit/schema/lint/_config.py:441` (currently `frozenset({"profile", "exclude", "min_severity", "max_warnings", "format"})`) plus matching extension of `ResolvedLintConfig` fields, `from_dict` precedence wiring, and `_coerce_*` helpers.** This is not assumed work; the existing allowlist hard-rejects any unknown top-level key with exit 2 (`error[lint-pyproject-config-invalid]:`), so introducing the knobs without atomic allowlist expansion would make every user's pyproject fail on upgrade. R9d (`schema_version`) is a wire-format output, not a pyproject input — unaffected by this allowlist constraint.
  - R9a. **Per-rule severity overrides** (`[tool.protokit.lint.severities]`): `severities = { "naming/enum-pascal-case" = "warning" }`. Lets teams demote individual rules from `error` → `warning` (or vice versa) without disabling them or leaving the chosen profile. **Semantics: user overrides always win.** After `LintProfile.compose()` returns its composed profile (with `rule_severity_overrides` resolved via the existing most-strict-wins semantics), the CLI applies the user's pyproject `severities` via `dataclasses.replace(composed_profile, rule_severity_overrides={**composed.rule_severity_overrides, **user_severities})` — the user's dict overlays the composed dict with user keys winning on collision. This preserves D2's compose semantics for built-in profile composition while ensuring user intent isn't silently discarded by a contributing profile's higher-severity declaration.
  - R9b. **DEFERRED TO D6b.** Per-rule disable/enable (`disabled_rules` / `enabled_rules` lists) had 4 collision shapes with undefined precedence semantics (rule in both lists; enabled-outside-profile; unknown rule_ids; profile + disable-of-canary). The right time to define R9b is against real D6a-shipping demand, not speculatively. At D6a, users needing to silence a single rule can use R9a to demote it to `info` (effectively suppressing it under default `min_severity = "warning"`).
  - R9c. **`--no-builtin-rules` flag** (CLI + pyproject equivalent). The load-bearing use case for D6a is the **BREAKING-opt-out path per R0** — protokit users on 0.1.x who don't want D6a's BREAKING auto-load expansion can use `--no-builtin-rules` to suppress every protokit-shipped pack and keep CI green while they review the new findings. (The secondary use case — users relying entirely on `--rule-pack MODULE` user packs — depends on the D7 plugin-loading path; D6a ships the flag so the opt-out is available, but the "user packs as primary rule source" workflow isn't operational until D7.) Pyproject equivalent key shape (`builtin_rules = false`? `no_builtin_rules = true`?) finalized in /ce:plan; allowlist expansion per the R9 prerequisite applies.
  - R9d. **`schema_version` field** in `lint_json` root and corresponding SARIF `runs[].properties.lint_schema_version`. Pre-committed by D5 plan §"TODOS.md refresh MUST include an explicit D6 line-item for JSON schema versioning" — D6a IS the next BREAKING wire-format change (R1's 20 new rules add new `rule_id` values to `lint_json` output), so the deferral cost amortizes here.

### Parity test infrastructure

- R10. Parity tests live in-repo at `tests/parity/` and are gated by an `@pytest.mark.parity` marker registered in `pyproject.toml` alongside the existing `slow` marker. Default `pytest tests/` skips the marker. Contributors and end users running the package never touch buf; only CI's dedicated parity job does.
- R11. CI gains one dedicated `parity` job that installs `buf` from its release bucket (version explicitly pinned in the CI workflow), runs `pytest tests/parity/`, and asserts protokit's rule-id and finding-location output is equivalent to buf's `buf lint` output on the same `.proto` fixture for every rule with a documented buf-equivalent in R2.
- R12. The differentiator seed (R6) does NOT have a parity test — no buf analogue exists. It has protokit-internal tests only.
- R13. The buf version pinned in CI is the parity contract. **Drift policy:** (a) the pinned version is surfaced in `protokit lint --version` output so users can see the parity reference without reading CI YAML; (b) pin bumps are quarterly by default — a maintainer reviews buf's release notes every quarter, decides whether to bump, and lands the bump + golden-fixture refresh in one PR with a CHANGELOG entry naming the new version; (c) urgent bumps (security advisory, behavior bug fix that affects parity claims) bypass the quarterly cadence; (d) divergence is documented when intentional (e.g., "protokit pins at v1.48 because v1.49 introduced behavior X that we explicitly do not mirror"). Bumping the buf pin is a deliberate act, but the cadence is bounded so the pin doesn't silently rot.

### Carry-over hardening (small)

- R14. Recalibrate `_LINT_HUMAN_SUMMARIZATION_THRESHOLD` from D5's placeholder `5` against real-world warning-count distributions. At 20-rule scale, the summarization threshold may need tuning — D6a is the first delivery with enough rules to surface meaningful warning counts. Threshold remains a module-level constant; tests pin behavior at N/N+1 boundaries via `monkeypatch.setattr` so the constant value is a zero-test-update knob.

## Key Decisions

- **Multi-delivery split (D6a + D6b) over single delivery.** Full buf DEFAULT parity is ~25-30 rules + cross-language + differentiator pack — too large to ship as one delivery without losing real-world feedback between authorship and ship. D6a (BASIC parity + seed) is the meaningful adoption checkpoint; D6b can react to D6a's reception before committing the rest. Rationale: lets us iterate the categorization, parity-fixture infra, and option-aware patterns on a smaller surface before sprawl.
- **Protokit-native profile vocabulary with buf aliases.** Primary names are `essentials`, `recommended`, `default`. Buf aliases `minimal` → `essentials` and `basic` → `recommended` are documented compatibility mappings resolved at config-load time. Buf users get a 1-line config rewrite; protokit's identity is not permanently coupled to buf's category taxonomy. Alternative considered: pure buf-mirror vocabulary (`minimal`/`basic`/`default`/`strict` as primary names) was rejected because it locks protokit into buf's category evolution permanently. Hybrid critique: the alias path leaves migrating users with one-time config friction (look up the alias) and persistent vocabulary mismatch with docs/help text — accepted as a worthwhile trade for identity flexibility.
- **Cross-language `PACKAGE_SAME_*` rules deferred entirely to D6b.** Originally framed as an opt-in pack within D6a, this was challenged by 3 reviewers (product-lens, adversarial, scope-guardian) — buf's BASIC *includes* cross-language by default, so any team running buf with `PACKAGE_SAME_*` enabled cannot drop-in migrate to protokit's `recommended` profile. Rather than ship cross-language with a misleading "uninstall buf" claim, D6a is honestly a single-language-team migration target; D6b ships cross-language alongside DEFAULT-tier rules so multi-language migration is a coherent single delivery. This also removes 7 rules' worth of parity-test fixtures from D6a's CI cost.
- **Differentiator seed (R6) chosen for ease over breadth.** `options/deprecated-must-have-replacement-comment` uses one built-in option (`deprecated`), no new pyproject config, and combines option-introspection + comment-introspection — exercising both of protokit's structural advantages. Alternative considered: `options/required-custom-annotation` (generic, pyproject-driven) was rejected for D6a because it requires NEW pyproject config schema. Defer to D6b.
- **Parity tests in-repo, dedicated CI job, buf binary pinned.** Highest fidelity (catches buf evolution at every CI run) without forcing buf installation on end users or default-pytest contributors. The pinned buf version IS the parity contract. Alternatives considered: spec-derived golden fixtures (no buf binary, but doesn't catch buf evolution) and documentation-only equivalence claims (rejected as unverifiable). Hybrid (goldens + drift check) was rejected as too much infrastructure for one delivery.
- **D5-deferred config knobs split: R9a + R9c + R9d ship in D6a; R9b deferred to D6b.** Three knobs become meaningful at 20-rule scale: R9a (per-rule severity overrides — common need), R9c (`--no-builtin-rules` — load-bearing as the R0 BREAKING opt-out path), and R9d (`schema_version` — D5 pre-commitment + structurally separate, see below). R9b (per-rule `disabled_rules` / `enabled_rules` lists) deferred because its 4 collision-shape precedence semantics need real demand to design against; the R9a severity-demote-to-`info` pattern is the D6a workaround.
- **R9d structurally separate from R9a/R9c despite group naming.** R9d (`schema_version`) is a wire-format output field, not a pyproject input — no `_ALLOWED_KEYS` expansion, no `ResolvedLintConfig` field, no `from_dict` wiring. It lives entirely at the formatter layer. Grouped under "config knobs" only because of D5's deferral framing; /ce:plan should treat it as a separate implementation unit from R9a/R9c.
